# META GAMES — единая программа оптимизации рендеринга

**Решение владельца: 06.11.2026. Статус: PLAN — ни одна оптимизация этим документом не считается внедрённой.**

Цель: применить методы Minecraft, Sodium, Distant Horizons, Nvidium и Voxy ко **всем играм META GAMES, где метод технически уместен**, через один общий рендерный слой и адаптеры; ускорить телефоны и ПК, уменьшить CPU/GPU, draw calls, геометрию и память **без ухудшения принятой графики, анимации, физики, геймплея, атмосферы и доступности объектов**.

Это дополнение к [основной цели](META_GAMES_PLATFORM.md), [ВИДИМО И ЭКОНОМНО](../05-proizvoditelnost-i-razvitie/VIDIMO_I_EKONOMNO.md), [GRAF](../01-stil-i-grafika/graf.md) и [разрешённым исходникам](../06-rabota-ii-s-kodom/META_GAMES_SOURCE_ALLOWLIST.md). Нельзя менять защищённые файлы, исходные OWNER PASS, каркас бота, пять автозадач и Netlify. Не создавать копий общих модулей внутри игр. Оптимизации применять в рабочих копиях `games/<игра>/` по одной игре за раз; на опубликованную карточку переключать только после успешной проверки существующим ботом и согласованного выпуска.

**Важно:** перечисленные технологии — идеи и алгоритмы, а не разрешение копировать исходники или ассеты Minecraft/модов. Новые инфраструктурные реализации писать самостоятельно либо из разрешённых источников и зависимостей с подтверждённой лицензией. Гарантированные проценты ускорения/экономии не обещать.

## 1. Область применения и классы сцен

| Тип игры/сцены | Обязательная основа | Оптимизации по показаниям | Что нельзя делать механически |
|---|---|---|---|
| Воксельные, блоковые, редактируемые миры | Frustum, backface, секции, отсечение внутренних граней, управление чанками | Greedy meshing, упаковка вершин, lightmap, batching регионов, LOD, отсечение закрытых пещер | Пересобирать весь остров из-за одного блока; склеивать воду с непрозрачным камнем |
| Большие непрерывные ландшафты, острова, террасы | Frustum, streaming, LOD, региональные батчи | Компрессия атрибутов, инстансинг травы/деревьев, порталы для помещений | Заменять уникальную форму дальнего рельефа без проверки силуэта; выдавать mesh-LOD за voxel-greedy |
| Компактные 3D-арены, платформеры, города | Frustum, backface, инстансинг повторов, бюджет эффектов | Portal/room culling, HLOD для зданий, атрибуты, региональные батчи | «Спать» физику, важные события или логику, влияющую на проходимость |
| 2D/2.5D, Canvas, спрайты, интерфейс | Visibility по камере, batching спрайтов, атласы, пауза невидимых FX | Дискретные уровни детализации и упаковка атрибутов, если действительно применимы | Строить 16³ секции, greedy voxel meshes и 3D-пещерный culling для не-воксельной игры |
| Прозрачная вода, туман, частицы и постэффекты | Отдельные проходы, контроль overdraw и буферов | LOD частиц, уменьшение дальних проходов, инстансинг | Сливать прозрачные и непрозрачные меши одним батчем и ломать сортировку |

**«Во все игры» = для каждой игры проведён аудит и подключён единый контракт оптимизации с отмеченными применимыми методами.** Метод с отметкой `not_applicable` не надо имитировать. Игра не должна терять объекты/ассеты ради ускорения.

## 2. Десять методов и конкретный способ реализации

| № | Приём | Реализация в META GAMES | Ограничения / fallback |
|---|---|---|---|
| O1 | **Frustum Culling** | Считать bounding sphere/AABB объектов и групп регионов в мировых координатах; каждый кадр проверять видимость по шести плоскостям камеры. Не обновлять невидимые VFX покадрово; сохранять состояние событий. | Предусмотреть запас для движущихся/крупных объектов, каскадных теней и появлений; отдельная логика для миникарты/отражений. |
| O2 | **Backface Culling** | Для непрозрачных односторонних мешей правильный winding и `FrontSide` / `gl.CULL_FACE`. При генерации меша не выпускать грани, закрытые соседними непрозрачными блоками. | Двусторонние листья, ткань, знаки, тонкие плоскости — исключения; backface GPU **не равен** удалению внутренних граней при генерации. |
| O3 | **Cave / Portal Culling** | Для воксельных секций вычислить связность воздушных выходов (6 сторон) и консервативную видимость секций от камеры; для комнат/коридоров — порталы и граф зон. Инвалидация при разрушении/открытии дверей. | Только при корректной топологии; если видимость неизвестна — **показывать**. Не скрывать звук, врагов и события, влияющие на игру. |
| O4 | **Chunk Sections** | В блоковых мирах секция по умолчанию `16×16×16` блоков или другой размер после профиля. Отдельные версии меша и dirty flags для секции, соседних границ и света. Пересборка изменённых секций асинхронно, лимит работы за кадр. | Размер 16³ не навязывать большим ландшафтным heightmap; там отдельные terrain chunks/quadtree. Обеспечить бесшовный seeded streaming и ограничение RAM/GPU. |
| O5 | **Lightmap** | Материал/шейдер читает компактный `16×16` lookup для дискретных уровней sky/block light (или атлас/текстуру освещения под конкретную сцену). При смене времени суток менять uniform/lookup, а не пересоздавать геометрию. | Для динамических теней и HDR/PBR оставлять отдельный путь; не путать 16×16 цветовую таблицу с текстурой освещённости пространства. |
| O6 | **Vertex Compression** | Квантовать позиции относительно origin секции в `Uint16` при достаточной точности, UV — 16 бит, нормали/цвет/свет — `Uint8/Int8`; декодировать в GLSL, переиспользовать VBO. | Сравнивать силуэт, швы, z-fighting, нормали; высокоточные hero/physics меши сохраняют float при необходимости. «−40% VRAM» — гипотеза, не гарантия. |
| O7 | **Batching / Regions** | Группировать по материалу, атласу, прозрачности и пространственному региону; `InstancedMesh` для повторов, статические геометрии объединять при невозможности инстансинга; избегать лишних смен shader/program/texture и вызовов draw. | Слишком большой batch ухудшает culling; динамические и прозрачные объекты — отдельные корзины, с корректной сортировкой. |
| O8 | **GPU-driven rendering** | **Не выдавать Nvidium/Voxy за готовую браузерную возможность.** В WebGL2 — CPU culling + instancing и опциональный поддерживаемый multi-draw. Отдельный экспериментальный backend WebGPU: GPU compute visibility/indirect draws/LOD с профилем устройства и shader validation. | WebGL2 не имеет переносимого compute-shader/indirect-draw конвейера. На Safari/iPhone/WebView и неподдерживаемых GPU всегда рабочий WebGL2/WebGL1 fallback без изменения игры. |
| O9 | **LOD / HLOD (Distant Horizons)** | Разные детализации по экранному размеру, дистанции и бюджету; близко — полный меш/анимация/текстуры, далеко — упрощённый меш, агрегированные чанки, impostor/2.5D; hysteresis и плавная смена уровней, предзагрузка соседей. | Не изменять коллизии и доступность пути; без дыр и pop-in, отдельная оценка расстояния по устройству. Дальний ландшафт — силуэт/туман должны остаться художественно верными. |
| O10 | **Greedy Meshing** | Для вокселей строить маски открытых граней по каждому из 3 направлений; объединять только соседние копланарные клетки с одинаковым материалом, освещением/AO, прозрачностью и ориентацией. Генерировать один quad на прямоугольник. | Не объединять через швы материалов, теней, разные UV/атласы и разрушаемые границы; сохранять тайлинг текстур. Не подходит органической геометрии и большинству skinned meshes. |

Приоритет O1/O2/O7 — высокая повторяемая польза; O3/O4/O5/O10 — прежде всего воксельные/закрытые сцены; O9 — открытые миры; O8 — **только после** доказанного выигрыша O1–O7 и O9–O10.

## 3. Общая архитектура (создать при наступлении этапа реализации)

Пока `shared/` в репозитории **не создан**; перечисленное ниже — целевая структура, а не существующие файлы. Размещать код ровно один раз в `shared/render/` и подключать из игр адаптерами, с сохранением локального/offline запуска там, где он предусмотрен.

- `shared/render/capabilities.js` — поддержка WebGL1/WebGL2/WebGPU, расширений, лимитов, устройства, DPR, предсказуемый выбор backend/fallback.
- `shared/render/visibility/frustum.js`, `visibility/portal-cave.js` — bounds, региональная видимость, консервативный culling.
- `shared/render/world/chunk-manager.js`, `workers/mesh-worker.js` — streaming, dirty sections, очередь пересборок, управление lifetime буферов, межчанковые границы.
- `shared/render/mesh/greedy.js`, `mesh/packed-attributes.js` — генерация мешей и декодирование форматов в GLSL.
- `shared/render/light/lightmap.js` — компактная таблица света и частичные обновления texture/uniform.
- `shared/render/submit/regions.js`, `submit/instancing.js` — корзины материалов, instancing, batching.
- `shared/render/lod/lod-manager.js` — LOD/HLOD, кэш, hysteresis, streaming при движении камеры.
- `shared/render/backends/webgl.js`, `backends/webgpu-optional.js` — надёжный WebGL путь и отдельный прогрессивный WebGPU backend.
- `shared/render/adapters/three.js`, `adapters/raw-webgl.js`, `adapters/canvas2d.js` — минимальные точки подключения существующих игр, без переписывания их визуального движка.
- `shared/render/performance-controller.js` — лимиты кадра, частиц, дальности, геометрии, обновлений; сохраняет управление и gameplay.
- `shared/render/README.md` — контракт подключения, версия модуля, зависимости, разрешённый источник, примеры для уже перенесённых игр (не новый отчёт).

**Контракт адаптера:** `init(renderer,camera,scene,capabilities)`, `register(object,bounds,material,flags)`, `markDirty(region,kind)`, `update(frameTime,cameraState)`, `dispose()`. Каждая игра объявляет `renderOptimization` в своём manifest/config: `pipelineVersion`, `applicable`, `enabled` (по умолчанию false до проверки), `fallback`, `deviceProfiles`. Данные и API только для чтения в отладочной диагностике `window.__META_RENDER_STATS__`: fps/frame times, draw calls, triangles, chunks, rebuild queue, culled regions, geometry/texture counts. **Не добавлять управление, телепорт, бессмертие или скрытые команды в `window.__META_BOT__`.**

**Offline и file://:** если worker ES modules или внешняя загрузка запрещены контекстом запуска, использовать включённый в сборку worker Blob либо безопасную синхронную очередь с тайм-бюджетом. Не делать новые CDN runtime-зависимости. Android WebView, Steam/Electron и GitHub Pages используют один и тот же игровой исходник.

## 4. Порядок внедрения и критерии завершения

### Этап P0 — инвентаризация каждой игры (перед первым изменением)
1. Найти фактически доступные игры в `games/` и разрешённые оригинальные источники в `meta6`; каждую последующую загруженную Claude игру добавлять в очередь автоматически. Нельзя считать игру переносимой, пока её код отсутствует.
2. Для каждой записать технологию (Three.js/WebGL2/WebGL1/Canvas), 2D/2.5D/3D/voxel, динамику мира, количество вызовов draw, треугольников, чанков, частиц, JS heap, время CPU/GPU по возможности, длительность кадра p50/p95, ошибки WebGL, FPS на телефоне/ПК.
3. Сделать матрицу применимости O1–O10 со значениями `already`, `planned`, `not_applicable`, `blocked`. Не маркировать «готово» только по наличию `frustumCulled=true`.
4. Определить одинаковые камеры/шейдеры/форматы и реальные источники по allowlist. Никаких изменений в защищённых оригиналах.

### Этап P1 — универсальные быстрые улучшения
1. O1 bounds/frustum для объектов и регионов, O2 winding/backface для подходящих непрозрачных мешей.
2. O7 instancing повторяемой травы, камней, обломков, зданий, частиц, где geometry/material одинаковы; пространственные регионы не больше разумного радиуса culling.
3. Внедрить правило `active / dormant / sleeping` из «ВИДИМО И ЭКОНОМНО», сохранив дешёвую непрерывную симуляцию критических событий.
4. Переключаемый адаптер и fallback, без изменения визуального результата.

### Этап P2 — воксели и обновления мира
1. O4 секции/dirty flags, очереди и межчанковая согласованность, bounded cache и освобождение GPU-ресурсов.
2. O10 greedy meshing и исключение внутренних граней; отдельно opaque/translucent/animated и зависимости AO/UV.
3. O3 flood-fill воздушных проходов, маски связности секций и инвалидирование при появлении отверстия/разрушении/открытии двери.
4. Проверить при непрерывном движении, изменении блока, обрушении дома, плавании и падении: нет пустот, невидимых стен и устаревших мешей.

### Этап P3 — освещение и формат вершин
1. O5 отдельный lookup lightmap и обновление света без rebuild геометрии там, где используется дискретный свет; сохранить оригинальные шейдеры и динамические спецэффекты.
2. O6 packed vertex formats сначала на статических чанках, затем на дальних объектах. Упаковка выбирается по ошибке, не по рекламным процентам.
3. Сверить дневную/ночную сцену, рассвет, факелы, туман, неоновые руны и разрушения; сравнить размер GPU buffers и реальные frame times.

### Этап P4 — большие миры и расстояние
1. O9 chunk/quadtree LOD, HLOD дальних построек и декора, impostor/2.5D где это сохраняет художественный замысел.
2. Добавить hysteresis/crossfade или геометрические переходы без швов, ограничение загрузки/выгрузки; экранный приоритет по размеру и расстоянию.
3. O7 региональные батчи с раздельным сортированием прозрачных поверхностей и отдельными движущимися объектами.
4. Балансировать CPU (сборка/доставка чанков) и GPU (геометрия/overdraw), не увеличивать дальность вслепую.

### Этап P5 — GPU-driven эксперимент, не блокирует остальные
1. Сначала собрать профили реальных поддерживаемых устройств. Для WebGL2 оценить `WEBGL_multi_draw`, если расширение действительно доступно; при отсутствии не включать.
2. Только для устройств с WebGPU построить альтернативный compute-culling + indirect submission; избегать дублирования всего игрового движка.
3. Сравнить с оптимизированным WebGL2, а не с исходным медленным рендером. Если выигрыша нет или меняется изображение/проходимость — оставить выключенным.

### Этап P6 — последовательное распространение на все игры
1. Подключать **одну игру за раз**, сохраняя старую версию и неизменные OWNER PASS-оригиналы. Сначала доступные `games/`; новая Claude-игра автоматически попадает в аудит и получает набор применимых методов.
2. Использовать один и тот же `shared/render/`: исправление общего рендера должно улучшать всех потребителей, а не создавать копии.
3. На каждом шаге сверять визуальный силуэт, видимость событий, физику/коллизии, управление пальцем, звук и проход уровня существующим ботом; не создавать новую служебную систему отчётов или тестов.
4. Если выявлена регрессия, отключить соответствующий флаг только для проблемного устройства/игры; исправить; не переключать ссылку каталога до успешной проверки.

## 6. Устройства, адаптация и численные ориентиры

- Профили: `mobile-low` (iPhone 11 / средний Android WebView), `mobile-high`, `desktop-webgl2`, `desktop-webgpu-optional`. Возможности определяет runtime, а не user-agent.
- Ориентир: `60 FPS` на ПК (бюджет **16,7 мс** на кадр), `30–60 FPS` на мобильном (**33,3–16,7 мс**); не превращать эти ориентиры в выдуманный PASS для любого устройства.
- Сравнивать в одинаковых точках камеры и при одинаковых эффектах: frame-time p50/p95, draw calls, triangles/vertices, CPU duration rebuilds, число загруженных чанков и сбросов GPU, JS heap, texture/geometry counts. `renderer.info.memory` **не равен** достоверному объёму VRAM.
- Включать оптимизацию, только если нет ошибок/визуальных и функциональных регрессий и есть измеримое улучшение узкого места на целевом устройстве; не объявлять выигрыш по одному FPS на пустой сцене.
- Регулятор качества: сначала бюджет частиц/далёкие FX, затем LOD, радиус активности и дальность детализации, и лишь затем render scale. Сохранять логические коллизии, навигацию, обзор цели и управление.
- При сбое/отсутствии WebGL2/WebGPU автоматически возвращаться на рабочий ранее совместимый backend. Компиляция GLSL, восстановление контекста и очистка ресурсов должны быть предусмотрены.

## 7. Завершение задачи

Работа считается реально завершённой **не после появления этого плана**, а когда для каждой игры с доступным кодом:
1. Есть корректная матрица `O1–O10` с `enabled / not_applicable / blocked` и измеренный baseline.
2. Все применимые и выигрышные методы подключены из общего кода и реально работают на ПК и телефоне; неподдерживаемые корректно отключаются.
3. Зримо не потеряны ассеты, объекты, атмосферные эффекты, вода, туман, свет, анимации, физика и gameplay; нет швов и пропавших событий за кадром.
4. Существующий бот проходит каждый уровень, нет новых ошибок и деградации кадра на тех же устройствах, на которых измерен baseline.
5. Каталог показывает проверенную версию, принятый оригинал доступен без изменений, и новые Claude-игры наследуют эту программу автоматически.
6. Статусы `PLAN`, `IMPLEMENTED`, `MEASURED`, `DEPLOYED` и `OWNER_ACCEPTED` не смешиваются. Итоговую художественную оценку `PASS/FAIL` даёт только владелец.
